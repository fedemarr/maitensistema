Veredicto rápido

Lo que recibiste es un prototipo válido con un modelo de negocio muy bien pensado, montado sobre una base técnica que no se puede llevar a producción tal cual. El pensamiento de producto (los .md de Lautaro) es excelente y se conserva entero. La implementación —un HTML de 6.980 líneas y una "base de datos" que es un único JSON— hay que rehacerla.

Estás en el mejor momento posible para rehacerla: 2 productos cargados, 0 ventas, 1 usuario. Recomiendo reconstruir sobre Next.js + Supabase normalizado ahora, y no después de acumular datos reales. No subas el maiten.html actual a un dominio público — hoy es una base de datos sin candado.

Cómo está armado hoy

  • Frontend: un <script> con ~300 funciones globales (rProds, rClis, stRender…). Sin módulos, sin tipos, sin build, sin tests. JavaScript ES5 (var, function).
  • Backend: Supabase. Pero se usa como un balde: toda la operación del negocio vive en una fila de la tabla app_state, en un solo blob JSON.
  • Persistencia: offline-first. El estado se serializa a localStorage (key lc6) y se sube a Supabase con upsert en segundo plano.
  • Auth: no hay. Un for compara usuario y contraseña contra un array en el propio JS.
  • Sin git. El propio handoff lo marca como "prioridad cero".

02 · Hallazgos críticos — bloquean el deploy

Cinco cosas que hacen inseguro exponer el sistema como está. Ninguna es culpa del diseño de negocio; son consecuencia de que el prototipo nunca fue pensado para estar en internet.

La base de datos está abierta al público

Seguridad

La policy de RLS es using(true) with check(true) y la publishable key está incrustada en el HTML (y repetida en tres .md y en Maiten.txt). Con esa URL y esa key, cualquiera puede leer, sobrescribir o borrar toda la base con un curl. La función resetearDatos() hace un DELETE de la fila sin ninguna autenticación.

Si subís esto a Vercel tal cual, publicás una base de datos sin llave. Un bot que rastree el repo o cualquiera que abra "ver código fuente" tiene control total.

Contraseñas en texto plano

Seguridad

{usuario:'admin', pass:'CREDENCIAL_REDACTADA', rol:'admin'} se guarda tal cual dentro del blob JSON — que, por el punto anterior, es de lectura pública. Cuando agregues usuarios para las socias, cada contraseña queda a la vista.

No hay autenticación real

Seguridad

El login compara strings en el navegador. Se saltea desde la consola del navegador ocultando el <div id="login"> o llamando a goTo(...) directo. El control de roles (PR[usr.rol]) también es solo visual: oculta botones del sidebar, no protege datos.

La función de IA no funciona y, si la arreglás mal, filtra la key

Seguridad

En iaSend() (línea ~2592) se hace fetch a api.anthropic.com desde el navegador sin header x-api-key: hoy devuelve 401 y nunca respondió. Si le pegás la API key ahí para que ande, queda expuesta a cualquier usuario. Esa llamada tiene que vivir en el servidor. El modelo que pide (claude-sonnet-4-20250514) además está discontinuado.

Secretos versionados y sin rotar

Higiene

La URL y la key del proyecto Supabase están en cuatro archivos de texto. Antes de poner nada en un repo, hay que rotar esas credenciales (o crear un proyecto nuevo) y mover todo a variables de entorno.

03 · Hallazgos de arquitectura — te van a frenar el crecimiento

Todo el negocio en una fila y un blob JSON

Datos

Cada cambio —marcar una venta, editar un precio— reescribe el estado completo de la aplicación. Dos consecuencias graves:

Pérdida silenciosa de datos con más de un usuario. Si Nati y una socia guardan algo el mismo rato, la última en escribir pisa a la primera (last-write-wins). Este es el problema que te va a morder apenas dos personas usen el sistema el mismo día.

No escala. Sin queries, sin índices, sin integridad referencial. Cada reporte carga el JSON entero a memoria y filtra en JS. A unos pocos miles de movimientos el blob pesa varios MB y cada carga y cada guardado se arrastran.

Sin trazabilidad

Datos

Existe un array auditoria pero está vacío y nada lo llena. No hay registro de quién cambió qué ni cuándo — algo que el propio backlog marca como bloqueante para producción.

Monolito de 6.980 líneas, scope global único

Código

Todo comparte el mismo espacio de nombres. No hay forma de testear una pieza aislada, y dos personas tocando el archivo produce conflictos de merge garantizados (el handoff lo dice explícitamente). Sin TypeScript, cualquier cambio de forma de dato se descubre en runtime.

Herencia del club de rugby sin limpiar

Deuda

Modelo de variantes "dummy" (talle/color) que no representa nada real; módulos de rugby ocultos pero presentes en el código; hardcodes "Rugby/Hockey/Extras" en formularios; un select de "deporte" en el alta de rubros; colores celestes sueltos que no son de la paleta Maitén. Rehacer limpio elimina toda esta clase de bugs de raíz.

04 · Qué se rescata — y es mucho

El valor del proyecto no está en el código: está en que el problema ya está entendido y modelado. Nada de esto se tira.

  • El diseño de dominio. Los .md de Lautaro son la especificación del producto: 8 tipos de movimiento (ingreso, venta, consignación, canje, presentación, regalo, rotura, devolución), consignaciones con vencimiento y estado, CC de clientes y proveedores, producción por lotes, reporte económico mensual. Eso es oro y se implementa tal cual.
  • La lógica contable de partida doble ya está diseñada y rodada con el club. Se porta.
  • La UX de cada módulo ya fue pensada y validada en uso real. Sirve como referencia visual directa.
  • Supabase como backend es la elección correcta. El problema es cómo se usa (un blob), no la herramienta.
  • La marca ya está aplicada: paleta oficial (verde oliva #7A8B5C / coral #E8A87C / crema) y logos en el brand book.

Migración de datos

Un script único que lee el blob JSON actual y lo inserta normalizado. Es trivial: hoy hay 2 productos, 0 ventas y 1 usuario. Cada semana de uso real de la versión vieja hace esta migración más cara — otro motivo para rehacer ahora.

07 · La decisión que necesito de vos

Antes de escribir una línea, definí cuál de estos dos caminos tomamos.

RECOMENDADO   Reconstruir sobre Next.js + Supabase normalizado, ahora.

Estás en el punto ideal: casi no hay datos ni usuarios, y todo el diseño de producto ya está hecho en los .md. Reescribís la implementación, no el pensamiento. En ~1 semana tenés el esqueleto en Vercel y de ahí portás módulo por módulo, con cada uno usable al terminarlo.

ALTERNATIVA   Asegurar el HTML actual y deployarlo en 2–3 días.

Sirve para una demo rápida a las socias: Auth real, RLS cerrado, keys rotadas, IA movida al servidor. Pero seguís arrastrando el blob JSON y el monolito, vas a chocar con el last-write-wins apenas haya dos usuarios, y vas a reescribir igual en un par de meses — con más datos y más caro.

Si vas por el camino recomendado, mi primer paso concreto es la Fase 0 y el scaffold del proyecto nuevo.
